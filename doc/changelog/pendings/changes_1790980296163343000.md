`playercreateinfo`, `playercreateinfo_action` and `playercreateinfo_item` now select rows with a
race/class bitmask, matching `playercreateinfo_skills`, `playercreateinfo_cast_spell` and
`playercreateinfo_spell_custom`, which already did. The `race` and `class` columns are replaced by
`raceMask` and `classMask`, so one row can now cover several races and classes.

### How to upgrade

Existing rows, custom ones included, are converted in place by the migration. Nothing needs
re-entering, and start positions that a realm has moved are kept.

**Race and class ids above 32 cannot be converted**, because a mask is 32 bits and there is no bit
to hold them. The update checks for them before it changes anything and stops with

> A race or class id above 32 does not fit a 32 bit mask. Remap or remove those rows, then re-run.

leaving all three tables as they were. Find them with

```sql
SELECT * FROM playercreateinfo WHERE race > 32 OR class > 32;
```

and the same on `playercreateinfo_action` and `playercreateinfo_item`, then remap or remove them and
run the update again. Nothing needs undoing first.

SQL that **writes** these tables does need updating. Race and class ids are 1-based, so an id `n`
becomes `1 << (n - 1)`: race 3 (Dwarf) becomes `raceMask` 4, class 3 (Hunter) becomes `classMask` 4.
Anything reading `playercreateinfo.race` or `.class` needs the new column names.

A stored 0 keeps meaning "all" in `playercreateinfo_action` and `playercreateinfo_item`.
`playercreateinfo` is the exception: it now refuses an empty mask and logs an `sql.sql` error,
because that table creates the race/class pairs rather than decorating existing ones, so "all" there
would invent pairs the game does not have, such as a human shaman, and offer them at character
creation. Every row there has to name its races and its classes.

Positional inserts are the dangerous case, because they keep working while meaning something else.
A statement like `INSERT INTO playercreateinfo VALUES (3, 1, ...)` meant dwarf warrior and now means
human plus orc warrior, and the row count is unchanged so nothing reports a problem.

Two modules are affected:

- **mod-arac** ([heyitsbench/mod-arac](https://github.com/heyitsbench/mod-arac)) inserts
  positionally into both `playercreateinfo` and `playercreateinfo_action`. Applied after this
  change, every row lands without error while covering the wrong combinations: 100 race/class
  combinations become 65, with 16 covered by more than one row. Characters belonging to a
  combination that is no longer defined stop appearing in the character list and cannot be loaded.
- **mod-worgoblin** ([heyitsbench/mod-worgoblin](https://github.com/heyitsbench/mod-worgoblin))
  names the column in every statement that touches these tables, both its `DELETE`s and its
  `INSERT`s, so applying it to a converted database fails immediately with
  `Unknown column 'race'` and changes nothing. Loud and harmless, but it still needs updating.

Update either module before applying this.

One row class is dropped by the migration: a `playercreateinfo_action` row with `race` or `class`
set to 0. Such a row did nothing before, because it resolved to a race or class that does not exist,
but as a mask 0 means "all" and the row would suddenly apply to every character. The shipped data
has none; this only affects custom rows.

Overlapping masks are now representable, where one row per race/class pair made them impossible.
All three loaders log an `sql.sql` error when two rows cover the same pair.
